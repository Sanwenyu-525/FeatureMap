# v0.2 Release Gate — Anchor-driven Feature Mapping

- Status: Accepted
- Scope: Phase 2, Milestones 6–9 (v0.2.0–v0.2.4), per ADR-0003
- Supersedes: ad-hoc milestone exit criteria for release judgment (the
  milestone exit criteria remain the per-milestone definition of done)

The release question is not "are all features implemented?" but:

> Given a feature entry point, can the system surface the code that
> truly matters without producing enough noise to destroy trust — and
> can developers understand, confirm, and correct the result?

Acceptance is layered: functional correctness, mapping quality,
explainability, performance, and real-world usability.

#### Anchor usage guidance

Anchor choice is the single largest lever on candidate quality
(measured on dify's `explore`: 1 → 99 candidates after re-anchoring,
`docs/reports/v0.2-release-gate-2026-09-01.md` §3). Rule of thumb per
feature shape:

- **HTTP feature** — no anchor needed: endpoints (`POST /api/login`)
  anchor automatically via route discovery.
- **Route-driven screen** (Next.js page/layout, Vue route component) —
  anchor the **route entry file** (`app/explore/layout.tsx` /
  `page.tsx`) as a `file` anchor, **not the component hub**
  (`app/components/explore/index.tsx`). A hub only reaches its own
  imports; the route entry pulls in the whole screen's component tree.
- **Library / CLI internals** (no HTTP surface) — anchor the exported
  entry (`file` or `symbol`) so the feature is discoverable at all.
- **Shared infrastructure** — never anchor logger/config/UI
  primitives; they are dependencies, not features.

Declared anchor types (`featuremap.yaml` `features.anchors`):

| type | target | when |
| --- | --- | --- |
| `file` | repo-relative path | entry file (page / layout / route entry) |
| `symbol` | `symbol:<path>:<Name>` | a specific exported symbol |
| `route` | endpoint name (`POST /api/login`) | endpoint features (redundant with auto-discovery) |
| `component` | `symbol:<path>:<Component>` | component-tree roots |

## 2. Quality Gate (Precision first)

### Fixture suite

Six fixture repositories, each with a ground-truth mapping
(`expected` / `notExpected` symbol lists) checked into the fixture
directory:

```text
test-fixtures/
  01-simple-login      single-feature JS/TS login
  02-react-login       React component tree + hooks + service
  03-nextjs-auth       Next.js app router + path aliases
  04-shared-utils      multiple features sharing logger/config/http
  05-monorepo          pnpm workspaces + cross-package imports
  06-cross-feature     two features sharing one boundary file
```

Ground-truth format per fixture:

```yaml
feature: login
anchors:
  - type: file
    target: src/login/LoginPage.tsx
expected: []       # symbols that must be surfaced
notExpected: []    # symbols that must NOT be surfaced as ownership
```

### Thresholds

```text
Core fixtures (01, 02, 03):  Precision >= 85%, Recall >= 70%
All fixtures (average):      Precision >= 80%, Recall >= 65%
Shared-infrastructure
false-positive rate:         < 10%  (04, 05, 06)
```

Precision outranks recall: a missed symbol can be accepted by hand;
fifty wrong symbols per feature kills the product (ADR-0003 §5).

### Shared-code pollution (part of the Blocker rationale)

Fixtures 04–06 must show:

```text
Login
├── AuthService.login        96%
├── UserRepository           86%
└── Logger                   24%   shared infrastructure
```

- high fan-in code is significantly down-weighted
- shared utilities do not enter high-confidence candidates by default
- infrastructure may appear as a dependency, never as ownership

## 3. Performance Gate

Values are a v0.2 gate, not a permanent SLA. Measure and record the
baseline first; calibrate thresholds against real benchmark results
before enforcing.

```text
Small  (100 files):   full < 2s      incremental < 500ms
Medium (1000 files):  full < 10s     incremental < 2s
                      peak memory < 1 GB
Large  (5000 files):  completes, no OOM, no hang
                      (no strict time gate in v0.2)
```

Benchmarks report: scan duration, peak memory, files parsed, evidence
records emitted, cache hit rate (AGENTS.md §12). Benchmark scripts and
results are checked in; "it feels fast" is not a result.

## 4. Review-loop drift (known limitation, non-blocker)

Rejected relations stay suppressed while their evidence chain is
stable. If the underlying code changes so that the relation is
essentially new (e.g. `Login → OldService` rejected, then `OldService`
renamed to `LoginService`), rejection must not permanently suppress
the new relation.

v0.2 records a relation fingerprint (evidence-chain hash) with each
verdict. Rejections whose fingerprint no longer matches are surfaced
as `superseded` for re-review rather than silently reapplied or
silently dropped. Automated semantic equivalence is explicitly out of
scope for v0.2.

## 5. End-to-end acceptance scenario

Run last; this is the release decision scenario.

1. User defines only an anchor:

   ```yaml
   feature: login
   anchors:
     - type: file
       target: src/app/login/page.tsx
   ```

2. `featuremap scan login` produces ranked candidates.

3. Output contains high-confidence feature code, lower-confidence
   transitive collaborators, and down-weighted shared infrastructure —
   each with evidence.

4. User accepts the core candidates and rejects the noise
   (`Logger`, `Button`).

5. Rescan: accepted candidates appear as confirmed; rejected
   candidates do not reappear; remaining suggestions still surface.

6. `featuremap explain login UserRepository.findByEmail` renders the
   full chain:

   ```text
   LoginPage
    ↓ renders
   LoginForm
    ↓ calls
   login()
    ↓ calls
   AuthService.login()
    ↓ calls
   UserRepository.findByEmail()
   ```

7. Modify one related file; rescan re-analyzes only affected graph
   regions.

If this scenario holds stably end to end, Phase 2 acceptance passes.

## 6. Usability acceptance

A person who did not develop the scoring runs
`featuremap scan login` and answers:

1. **Can they see why `AuthService.login` belongs to Login?**
   If a developer explanation is required → fail (evidence problem).
2. **Do they naturally find how to exclude a wrong candidate?**
   They should reach `reject` unaided.
3. **Would they accept a recommendation without hand-verifying it?**
   "I'd have to check every one in the source" → fail
   (precision or evidence insufficient).
